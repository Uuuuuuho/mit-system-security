# Lab 3: Transient execution in a CPU model (`specsim`)

In this lab you attack and defend a CPU whose microarchitecture you can read in a
few hundred lines of Python. `specsim` is a small, cycle-approximate
out-of-order-ish core with a branch predictor, a reorder buffer, a two-level
cache, `clflush`/`rdcycle`/`fence`, and two privilege levels with a toy kernel.
You write attacker programs in its assembly language, usually generated by short
Python helpers, and run them against kernel victims through system calls.

**Simulator only.** All transient-execution work in this lab runs inside
`specsim`. There is no native backend, and none is planned: per the lab-suite
safety rules, Spectre-style code never runs on real hardware here. The simulator
is deterministic for a given `SEED`, needs only Python 3 (standard library), and
behaves the same on x86_64 and aarch64, including Docker on Apple silicon.

| Part | What you do | Mode | Time |
|---|---|---|---|
| 1 | Flush+Reload through a system call (architectural leak) | sim | ~1.5 h |
| 2 | Spectre v1: bounds-check bypass against a kernel gadget | sim | ~2 h |
| 3 | Spectre v1 with a short window: widen it with an eviction set | sim | ~2.5 h |
| 4 | Four defenses (fence, SLH, InvisiSpec-like, STT-like): leakage and overhead | sim | ~4 h |

## Learning goals

* Explain why a squashed instruction can still leak: the squash restores
  architectural state, but it does not undo microarchitectural state such as
  cache contents.
* Build a working Flush+Reload receiver: calibration, flushing, timing and
  decoding with noise.
* Mount Spectre v1 end to end: train the predictor, open the window, transmit
  through the cache, decode.
* Reason quantitatively about the speculation window (branch-resolution latency
  versus the gadget's critical path), and control it from user code with an
  eviction set.
* Implement software defenses (fences, speculative load hardening) as compiler
  passes and hardware defenses (InvisiSpec, STT) as core policies. Measure what
  they stop and what they cost, and place them in the hardware-software contract
  framework.

**Lecture mapping.** This lab covers lectures L04–L06. Parts 1–3 follow the
transient-execution attack material (Spectre and Meltdown, cache covert
channels). Part 4 follows the defense material: hardware schemes such as
InvisiSpec, STT and NDA; software schemes such as fences and speculative load
hardening; and the hardware-software contract view of what speculation may
leak.

## The machine

### Microarchitecture

```
                 +---------------------------+
  PHT: 2-bit     |  fetch + predict          |<--------------------------------+
  counters/PC -->|  (front-end follows the   |                                 |
  BTB: jalr  --->|   predicted path)         |                                 |
                 +-------------+-------------+                                 |
                               | up to 4 instructions / cycle, in order        |
                               v                                               |
                 +---------------------------+   ROB: 128 entries;             |
                 |  dispatch into the ROB    |   retire in order               |
                 +-------------+-------------+                                 |
                               | issue as soon as all source registers are ready
        +----------------+-----+-----------+---------------------+             |
        v                v                 v                     v             |
   +---------+    +-------------+   +-------------+   +----------------------+ |
   |  ALU    |    | branch unit |   | load/store  |   | fence, rdcycle,      | |
   | 1 cycle |    | resolves 1  |   | unit        |   | syscall, sysret,     | |
   | mul 4   |    | cycle after |   |             |   | halt: serialize      | |
   | div 16  |    | its operands|   |             |   +----------------------+ |
   +---------+    +------+------+   +------+------+                            |
                         |                 |   Policy hook (Part 4)            |
                         | mispredicted?   |   sees every load                 |
                         +-----------------|-----------------------------------+
                           squash: registers and stores are discarded,
                           restart at resolve + 10 cycles
                                           v   loads that issued on the wrong path
                                               have ALREADY filled the caches
   +---------------------+    +-------------------------+    +----------------+
   | L1D 32 KiB          |    | L2 2 MiB, inclusive     |    | DRAM           |
   | 64 sets x 8 ways    |--->| 2048 sets x 16 ways     |--->| ~150 cycles    |
   | LRU, ~4 cycles      |    | LRU, ~14 cycles         |    | (140..170)     |
   +---------------------+    +-------------------------+    +----------------+
```

**Timing model.** The core executes instructions functionally in program order,
as an interpreter does. A dataflow timing model gives each instruction three
cycle numbers:

| | rule |
|---|---|
| dispatch `d` | in order, at most 4 per cycle, and only when a ROB entry is free (the instruction 128 places earlier must have retired) |
| issue `i` | `max(d, ready time of every source register)` |
| complete `c` | `i + latency`: ALU 1, `mul` 4, `divu`/`remu` 16, loads = cache latency |
| retire | in order: `max(c, retire of the previous instruction)` |

Independent instructions overlap, so several cache misses can be in flight at
once. A second access to a line whose fill is still in flight waits for that
fill.

**Speculation.** A conditional branch is predicted at dispatch and resolves one
cycle after its operands are ready. On a misprediction the core first runs the
*wrong path*. It keeps dispatching from the predicted target as long as

1. the dispatch cycle is before the branch's resolve cycle, and
2. a ROB entry is free (the stalled branch holds up retirement),

and it stops early at a serializing instruction (`fence`, `rdcycle`, `syscall`,
`sysret`, `halt`). A wrong-path instruction executes only if it *issues* before
the resolve cycle. Wrong-path instructions work on a copy of the register file
and a private store buffer, so the squash discards all of their architectural
effects. **Their cache fills stay.** The correct path then restarts at
`resolve + 10`.

```
cycle  d_b                                          resolve = (bound ready) + 1
         | bgeu dispatched, predicted "in bounds"            |
         |-- wrong path: lb secret -> slli -> add -> lb PROBE[secret*4096]
         |   (only instructions that ISSUE before resolve execute)
         |                                                   | squash: regs/stores gone,
         |                                                   | PROBE line stays cached
```

So the window is *the time the branch's operands take*. A bound that misses in
the cache gives about 150 cycles. A bound in L1 gives about 5. Nested
mispredictions on a wrong path are not explored: the inner branch simply
redirects. Wrong-path loads that would fault (for example, a user load of a
kernel address) return no data. The model is not Meltdown-vulnerable unless you
pass `meltdown=True`.

**`rdcycle` and `fence`.** `rdcycle rd` waits until every older instruction has
completed, returns that cycle number, and holds younger instructions back (it
behaves like `lfence; rdtsc; lfence`). For example,
`rdcycle t1; lb t0, 0(s0); rdcycle t2` gives `t2 - t1 = load latency + 1`.
`fence` makes younger instructions wait until every older instruction has
completed. On a wrong path, both instructions end speculation.

**Caches.** Lines are 64 B. Both levels use plain modulo indexing on physical
addresses: L1 set = `(addr >> 6) & 63`, L2 set = `(addr >> 6) & 2047`. Both are
LRU. L2 is inclusive, so evicting a line from L2 also removes it from L1. Stores
write-allocate. Every access gets a little latency noise, and about 0.2% of
accesses get an extra 80–300 cycle "interrupt" spike, so code that measures time
must tolerate occasional outliers. `clflush` removes a line from both levels.
User code may flush user lines only.

**Branch prediction.** The PHT has 1024 two-bit saturating counters, indexed by
PC and initialized to weakly not-taken; it predicts taken when the counter is at
least 2. `Machine(ghist_bits=n)` turns it into gshare. Direct jumps need no
prediction. `jalr`/`ret` use a BTB that remembers the last target for each PC;
when there is no entry, the front-end stalls. Only committed branches train the
predictor.

### Privilege, memory map and the kernel

```
0x0000_0000 - 0x000F_FFFF   unmapped (any access faults)
0x0010_0000 - 0x001F_FFFF   kernel data: kernel mode only
0x0020_0000 - 0x009F_FFFF   user memory: user + kernel
    0x0020_0000   .data of your programs (each loaded program gets its own slice)
    0x0040_0000   PROBE: 256 slots x 4096 B, shared with the kernel
    0x0050_0000   HEAP: free scratch memory (to 0x009E_FFFF)
    0x009F_0000   stack (sp = STACK_TOP = 0x00A0_0000)
0x4000_0000 / 0x8000_0000   user / kernel text: separate instruction memory, not readable as data
```

There is no MMU; privilege is checked by address range. Architecturally, a user
load or store to kernel memory, a user `clflush` of a kernel line, or a jump into
kernel text *faults*: the run stops with a `ProgramFault` that names the
offending source line.

User code enters the kernel with `syscall`: the number goes in `a7`, the
argument in `a0`, and the result comes back in `a0`. The kernel clobbers t0–t6
and a0, plus gp/tp when a Part 4 pass is applied. Read
[`specsim/kernel.s`](specsim/kernel.s) or run `python3 -m specsim kernel`:

| syscall | victim behaviour |
|---|---|
| `SYS_FR` (1) | `if (i < len) touch PROBE[secret1[i] * 4096]`: correct code with a secret-dependent access pattern (Part 1) |
| `SYS_V1` (2) | `clflush(&v1_limit); if (x < v1_limit) touch PROBE[v1_array[x] * 4096]` (Part 2) |
| `SYS_V1_HARD` (3) | same, but the bound is *not* flushed, and the index first goes through `mul/divu/mul/divu` (Part 3) |
| `SYS_NOP` (0) | returns 0 |

All `k_*` kernel data symbols (`k_v1_limit`, `k_v1_array`, `k_secret2`, ...)
are public, as in a System.map without KASLR. They are assembler symbols and are
also listed in `m.ksyms`. You know *where* the secrets are. You just cannot load
them.

### ISA reference

Registers are x0–x31 with the RISC-V ABI names (`zero ra sp gp tp t0–t6
s0–s11 a0–a7`). `zero` is hardwired to 0, and values are 64-bit.

| class | instructions | notes |
|---|---|---|
| ALU reg-reg | `add sub and or xor sll srl sra mul divu remu sltu slt  rd, rs1, rs2` | `mul` 4 cycles, `divu`/`remu` 16, others 1 |
| ALU reg-imm | `addi andi ori xori slli srli srai sltiu  rd, rs1, imm`; `li`/`la rd, imm` | any 64-bit immediate |
| loads | `ld lw lb  rd, off(rs1)` | 8/4/1 bytes, zero-extended |
| stores | `sd sw sb  rs2, off(rs1)` | |
| branches | `beq bne blt bge bltu bgeu  rs1, rs2, label` | predicted (PHT) |
| jumps | `jal [rd,] label`, `jalr rd, rs1[, imm]` | `jalr` predicted by the BTB |
| system | `fence`, `rdcycle rd`, `clflush off(rs1)`, `syscall`, `sysret` (kernel), `halt` (user), `nop` | see the timing rules above |
| pseudo | `mv not neg beqz bnez bgt ble bgtu bleu j call jr ret` | each expands to one instruction |

**Assembler syntax.** Comments start with `#` or `;`. Labels end with `:`.
The `.text` and `.data` directives switch sections. Data directives are
`.byte/.word/.quad e, ...`, `.zero N`, `.align N` (N in **bytes**), and
`.ascii`/`.asciz`. `.equ NAME, expr` defines a constant, and `.entry` marks an
entry point (it matters only for Part 4). Expressions may use `+ - * / % << >> &
| ^ ~`, parentheses, `'c'`, labels, and the predefined symbols `PROBE_BASE`,
`PROBE_STRIDE`, `PROBE_ENTRIES`, `HEAP_BASE`, `HEAP_END`, `STACK_TOP`,
`LINE_SIZE`, `SYS_*` and `k_*`. Every program needs a `_start` label and must
reach `halt`.

### Python API (`specsim.Machine`)

```python
m = Machine(seed=1)                       # Config fields as keywords: Machine(seed=1, ghist_bits=8)
prog = m.load(src)                        # assemble + load; same source again -> same Program, memory NOT reset
res  = m.run(prog, a0=x, a1=y)            # run from _start until halt; other regs 0, sp = STACK_TOP
res.cycles, res.instrs, res["a0"]         # results
m.read(addr, n) / m.read_u64s(addr, k)    # read user memory (prog["label"] gives a label's address)
m.write(addr, b) / m.write_u64s(addr, v)  # write user memory
m.ksyms, m.symbols, m.geometry            # kernel symbols, assembler symbols, cache geometry/latencies
m.PROBE_BASE, m.HEAP_BASE, m.SYS_V1 ...   # layout constants
m.user                                    # a dict for caching your own state between calls
m.run(prog, trace=print)                  # per-instruction trace: d/i/c cycles, '~' = transient
```

Caches, predictor, memory and the cycle counter persist across `run()` calls,
like successive time slices of one attacker process. Pass per-call values in
registers rather than generating a new source for every byte, because each
distinct source permanently takes space in the 2 MiB program-data area.

`python3 -m specsim run file.s [--trace] [--set a0=5] [--dump label:8]` runs a
file on a fresh machine. `python3 -m specsim info` prints the layout and
parameters. Here is a trace excerpt of the Part 2 attack call, where `~` marks
squashed instructions:

```
  d=  89888 i=  89889 c=  90058  K 0x80000070  ld      t1, 0(t0)               # bound (always a cache miss)
  d=  89888 i=  90058 c=  90059  K 0x80000074  bgeu    a0, t1, sys_v1_out      # bounds check
~ d=  89889 i=  89889 c=  89890  K 0x80000078  la      t2, k_v1_array
~ d=  89889 i=  89890 c=  89891  K 0x8000007c  add     t2, t2, a0
~ d=  89889 i=  89891 c=  89895  K 0x80000080  lb      t3, 0(t2)               # v1_array[x]
~ d=  89889 i=  89895 c=  89896  K 0x80000084  slli    t3, t3, 12
~ d=  89890 i=  89890 c=  89891  K 0x80000088  li      t4, PROBE_BASE
~ d=  89890 i=  89896 c=  89897  K 0x8000008c  add     t4, t4, t3
~ d=  89890 i=  89897 c=  90050  K 0x80000090  lb      t5, 0(t4)               # PROBE[v1_array[x] * 4096]
~ d=  89890 i=  89890 c=  89891  K 0x80000094  li      a0, 0
  d=  90069 i=  90069 c=  90070  K 0x80000094  li      a0, 0
```

The bound misses (cycle 89889 to 90058) and the branch resolves at 90059. In
between, the wrong path reads the secret byte (an L1 hit), and at cycle 89897 it
issues the load of `PROBE[secret * 4096]`. That fill completes after the squash,
but it is not undone. The correct path restarts at 90069 = 90059 + 10.

## Part 1: Flush+Reload through the syscall interface (sim, ~1.5 h)

`SYS_FR(i)` is a correct, bounds-checked system call that touches the shared
slot `PROBE[secret1[i] * 4096]`. You leak `secret1` with Flush+Reload: flush
every slot, let the kernel run, then time a reload of every slot.

**Exercise 1-1.** In `src/part1_flush_reload.py`, complete `CALIBRATE_SRC` and
`calibrate(m)`. Time cached and flushed loads with `rdcycle`, look at both
distributions, and return a threshold that separates them robustly despite the
spikes.

**Exercise 1-2.** Complete `LEAK_SRC` and `leak_byte(m, i)`. Flush all 256
slots, call `SYS_FR`, reload and time each slot, and decode. Retry when the
result is ambiguous. The grader requires *every* byte.

**Discussion 1-1.** Report your hit and miss latency distributions and your
threshold. During the reload, the slot that hits usually shows an L2 latency,
not an L1 latency. Why? Compute the L1 and L2 set of `PROBE_BASE + b * 4096`.

**Discussion 1-2.** `SYS_FR` has no bug in the usual sense and does not depend
on speculation. Why does it leak? Rewrite it in toy assembly so that its memory
access pattern is independent of the secret, and estimate the cost. Which of the
Part 4 defenses would you expect to stop this attack?

## Part 2: Spectre v1 (sim, ~2 h)

`SYS_V1(x)` is the classic gadget
`if (x < v1_limit) touch PROBE[v1_array[x] * 4096]`, and the kernel flushes
`v1_limit` on every call. `secret2` sits in kernel memory after `v1_array`.

**Exercise 2-1.** Complete `src/part2_spectre_v1.py`: `leak_byte(m, i)` must
return `secret2[i]`. You need to (1) train the bounds check with in-bounds
calls, (2) flush the probe array, (3) make one call with
`x = k_secret2 - k_v1_array + i`, and (4) reload and decode. The grader requires
at least 90% of the bytes.

**Discussion 2-1.** Use `trace=print` to trace one attack call. Give the cycle
at which the bound load issues and completes, when the branch resolves, and when
the secret load and the transmitting load issue. How large is the window, and
how many transient instructions run?

**Discussion 2-2.** For each byte, the first attempt usually fails and the second
succeeds. Explain why. What would change if the secret were never in the cache?
How many training calls do you need with 2-bit counters, and why? Does your
attack still work with `Machine(ghist_bits=8)` (gshare)?

**Discussion 2-3.** Apart from the bound's latency, what limits how far
speculation can run in this model? Estimate the maximum number of transient
instructions after a mispredicted branch whose operand misses in DRAM.

## Part 3: A short window (sim, ~2.5 h)

`SYS_V1_HARD` uses the same gadget with two changes: the bound `k_v1h_limit` is
no longer flushed, so after your training calls it sits in L1, and the index
goes through a slow, dependent `mul/divu/mul/divu` computation before the array
load. Run your Part 2 attack against it first. It should fail.

**Exercise 3-1.** In `src/part3_short_window.py`, implement
`eviction_set(m, target)`. It returns user addresses such that loading each one
(in order) evicts the line holding `target` from L1 *and* L2. You cannot
`clflush` a kernel line, but the caches are physically indexed and shared. Use
`m.geometry`, and take addresses from the HEAP.

**Exercise 3-2.** Implement `leak_byte(m, i)` for `secret3` through
`SYS_V1_HARD`, using your eviction set to make the bound miss again. Think about
*when* to evict. The grader requires at least 50% of the bytes.

**Discussion 3-1.** Using cycle numbers from traces, compute the window when the
bound is in L1, in L2 and in DRAM, and the gadget's critical path from branch
dispatch to the issue of the transmitting load. Explain exactly why the Part 2
attack fails here.

**Discussion 3-2.** Which address bits select the L2 set? Why do lines that are
congruent modulo 128 KiB also collide in L1? How many lines do you need under
LRU, and why does the inclusive L2 matter? Try `Machine(l2_repl="random")`: how
must the eviction strategy change? What would change with a hashed (sliced)
set index, as on many Intel CPUs?

## Part 4: Defenses (sim, ~4 h)

Implement four defenses in `src/part4_defenses.py`. The grader builds a machine
with each one, runs **your Part 2 attack** against it (10 secret bytes), checks
that the 7 programs in [`specsim/bench.py`](specsim/bench.py) still compute
correct results, and prints the leakage and the cycle overhead relative to the
undefended machine. The software passes are applied to the kernel *and* to the
benchmarks, as a compiler would recompile everything. The hardware policies
change the core. The grader also reports whether your Part 1 attack still works
under each defense (column `arch F+R`).

**Exercise 4-1: fence.** `fence_pass(src) -> src` inserts `fence` at the start
of both successors of every conditional branch. Use the helpers in
[`specsim/asmtools.py`](specsim/asmtools.py) (`parse`, `render`, `Line`).

**Exercise 4-2: speculative load hardening.** `slh_pass(src) -> src`
implements LLVM-style SLH. A predicate register `tp` is −1 on the correct path
and 0 on a mispredicted one. On every branch edge, AND into `tp` a mask computed
without branches (`asmtools.branch_taken` helps). Give the taken edge a
trampoline block, and harden every loaded value with `and rd, rd, tp`. `gp` and
`tp` are reserved for you, and `.entry` marks the places where `tp` must be
reset.

**Exercise 4-3: InvisiSpec-like.** `InvisiSpecPolicy.on_load`: a speculative
load must not change the cache. It reads with `caches.peek` and asks for the line
to be installed when (and if) it retires (`ev.expose = True`). See
[`specsim/policy.py`](specsim/policy.py) for the event fields: `ev.spec` means
an older branch is unresolved at issue, and `ev.vis` is the cycle at which the
load can no longer be squashed. Like real hardware, the policy cannot tell
whether a load is on the wrong path.

**Exercise 4-4: STT-like.** `STTPolicy`: the value returned by a speculative
load is tainted until the load's visibility point (`load_taint`). The core
propagates taint through ALU operations. A load whose *address* is tainted is a
transmitter and must not issue before the taint clears (`transmit_delay`).

A defense passes if your attack leaks at most 1 of the 10 bytes and the
benchmarks remain correct. For the two hardware policies, the geometric-mean
overhead must also stay under 30%: simply delaying or hiding *every* speculative
load blocks the attack too, but costs 35–55% here. For reference, the reference
solution measures roughly fence +150%, SLH +47%, InvisiSpec +9%, STT +4%. Treat
differences of ±2% as noise.

**Discussion 4-1.** Copy the defense table from `make check` into your report.
For each defense, explain its cost on at least two benchmarks. For example: why
does the fence pass hurt `sum` and `hist` so much more than `list`? Why does
InvisiSpec hurt `bsearch` and `filter` but not `sort`? Why are STT's costs
concentrated in `list` and `syscall`?

**Discussion 4-2.** All four defenses still allow the Part 1 leak. Relate this
to the hardware-software contract view (Guarnieri et al.). What does each
defense guarantee, in terms of what speculative execution may leak beyond
sequential (non-speculative) execution? What must software still guarantee on
its own? Which contract would `SYS_FR` need, and which programs does that rule
out?

**Discussion 4-3.** Describe one attack that at least one of your defenses does
*not* stop in principle, even if this model cannot express it, and sketch an
experiment in `specsim` that would show the gap. Candidates include implicit
channels through branch resolution under STT, other microarchitectural state
under InvisiSpec (TLB, predictor, MSHR or port contention), indirect branches
or returns under the fence pass, values used before they are hardened under SLH,
and Spectre-v2/RSB/STL variants.

## Grading

`make check` grades `src/`, and `make check-solution` grades `solutions/`.
Every byte runs under an instruction budget, which is generous: the reference
uses a fraction of it.

| item | points | pass condition |
|---|---|---|
| 1-1 | 5 | threshold in [20, 135] cycles |
| 1-2 | 15 | all bytes of `secret1` |
| 2 | 25 | at least 90% of `secret2` |
| 3-1 | 5 | touching your eviction set evicts `k_v1h_limit` (5 of 5 trials) |
| 3-2 | 20 | at least 50% of `secret3` |
| 4-fence, 4-slh, 4-invisispec, 4-stt | 4 x 7.5 | your Part 2 attack leaks at most 1 of 10 bytes; benchmarks correct; policies within +30% |

The exit status is 0 only if everything passes. The Discussion items go in
`report.md`.

## Hints

* Start by reading the traces of `examples/timing.s` and `examples/transient.s`.
* If your Flush+Reload sees *several* hits, something else touched those slots
  (training calls also touch a slot), or your threshold is wrong. If it sees
  *none*, either the spike noise hit you or the transmitting load never issued
  inside the window: look at the trace.
* Keep the attacker program fixed and pass the varying values (`x`, the training
  index) in registers.
* In Part 3, `m.geometry["l2_sets"] * 64` bytes is the distance between
  addresses that share an L2 set. Evicting after training and before the attack
  call matters.
* For the passes, look at what you generate. From the lab directory, run
  `PYTHONPATH=.:src python3 -c "from specsim import kernel_source; from part4_defenses import slh_pass; print(slh_pass(kernel_source()))"`.
  The output must still assemble, and the benchmarks must still produce correct
  results.

## Going further

* **Spectre v2.** The BTB is indexed by the full PC, so user and kernel jumps
  never alias. Change `predictor.py` to index by low PC bits, add a kernel victim
  with an indirect call, and poison the BTB from user mode.
* **Meltdown.** Run `Machine(meltdown=True)` and read kernel memory directly
  from a user-mode mispredicted path. Which Part 4 defenses still help?
* **Implicit channels and STT.** Write a gadget such as
  `if (secret & 1) touch A else touch B`, where A and B are constants, and show
  that your `STTPolicy` leaks through it. Then make wrong-path branches with
  tainted operands follow the prediction in `cpu.py:_wrong_path`, which is what
  the STT paper does, and show that the hole closes.
* **Random replacement.** Redo Part 3 with `l2_repl="random"`. How large must
  the eviction set be, or how many passes do you need, for 95% eviction?
* **Eviction sets without the geometry.** Find a set that evicts `k_v1h_limit`
  using only the timing of `SYS_V1_HARD` itself, with group testing (Vila et al.).
* **More policies.** Implement delay-on-miss (Sakalis et al.) or NDA-style
  propagation blocking (Weisse et al.) as a `Policy`, and compare security and
  overhead with your InvisiSpec and STT.
* **Prime+Probe.** Assume `PROBE` is not shared. Recover `secret2` through L2
  set contention instead of Flush+Reload.
